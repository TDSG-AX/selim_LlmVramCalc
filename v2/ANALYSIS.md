# v2 계산 근거·공식 정리 및 객관적 평가

대상: AI 코딩 에이전트 인프라 사이징 계산기(v2). 작성 기준은 v2 제작 시 정리된 설계 메모(컨텍스트 구간 가이드, 1차 함수 모델, 8종 가속기 구성)와 저장소의 `v2/index.html`입니다.

> **버전 불일치 주의**: 설계 메모는 가속기 8종(L40S×1, H100×1, GB10, A100×2, H100×2, L40S×4, H200×2, A100×4/H100×4)과 "컨텍스트 길이를 X축으로 하는 그래프"를 기술합니다. 현재 저장소의 `v2/index.html`은 **6종**(H100×1, GB10, A100×2, H100×2, H200×2, H100×4)이고 그래프의 X축은 **동시 인원**입니다. 이 문서는 공식·근거는 두 쪽에 공통인 것을 다루고, 차이는 "메모에만 있음"으로 표시했습니다. 반영 여부는 기능 검토 단계에서 결정합니다.

## 1. 계산 모델

### 1.1 필요 VRAM (1차 함수)

```
필요 VRAM(GB) = b + a × x
  b = 모델 가중치 + 런타임 버퍼        (고정, y절편)
  a = 1k 토큰당 KV Cache × 컨텍스트(k) (동시 인원 x일 때)
```

| 그래프 X축 | 기울기 a | 의미 |
| :--- | :--- | :--- |
| 동시 인원 N (현재 HTML) | `kvPer1k × 컨텍스트(k)` | 1인당 KV Cache |
| 컨텍스트 k (메모 버전) | `kvPer1k × N` | 32B·10인이면 약 1.31~1.4 GB/1k |

### 1.2 최대 동시 인원 / 한계 컨텍스트

```
최대 인원 = floor((장비 VRAM − b) / (kvPer1k × 컨텍스트k))
한계 컨텍스트(k) = (장비 VRAM − b) / (kvPer1k × N)
```
예: 32B FP16, b=76, 10인, 160GB → (160−76)/1.4 = **60k** (메모의 "약 60k 교차점"과 일치).

### 1.3 예상 속도 (decode, 메모리 대역폭 바운드)

```
tps ≈ (대역폭 × 0.62) / (가중치 + 1인당 KV) × max(0.5, 1 − 0.025·(N−1))
```
0.62는 메모리 대역폭 활용률(MBU) 가정, 판정 기준은 28 tps 이상입니다.

## 2. 입력값 근거 검증

KV Cache 크기는 모델 구조에서 직접 계산됩니다: `2(K,V) × 레이어 × KV헤드 × head_dim × 바이트`.

| 모델 | 레이어 / KV헤드 / head_dim | KV, FP8 (GB/1k tok) | KV, FP16 | 코드 값 | 판정 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Qwen 14B | 48 / 8 / 128 | 0.098 | 0.197 | 0.10 | 일치 |
| Qwen 32B | 64 / 8 / 128 | 0.131 | 0.262 | 0.14 | 일치(약 7% 보수적) |
| 70B급(Llama 3.x) | 80 / 8 / 128 | 0.164 | 0.328 | 0.17 | 일치 |

가중치: 14B FP16 ≈ 29.5GB(코드 30), 32B FP16 ≈ 65GB(코드 67), 32B INT4 ≈ 18~19GB(코드 19), 70B FP8 ≈ 71GB(코드 73) — 모두 타당합니다. 레이어·헤드 수는 공개된 Qwen2.5/Llama 3 계열 구성 기준이며, 실제 사용 모델(예: Qwen3, 코더 변형)로 바꾸면 재확인이 필요합니다.

**고정 버퍼(런타임 오버헤드) 7~11GB**는 CUDA 컨텍스트·activation·CUDA graph 등을 뭉뚱그린 경험값입니다. 방향은 맞지만 출처가 없으므로 실측 보정 대상입니다.

## 3. 컨텍스트 구간 가이드 평가 (8k~128k)

| 구간 | 메모의 구성(토큰) | 합계 검산 | 평가 |
| :--- | :--- | :--- | :--- |
| 8~16k | 2k+4k+4k | 10k | 타당 |
| 32k | 4k+15k+10k | 29k | 타당, 표준 구간 설정 합리적 |
| 64k | 40k+20k | 60k | 타당 |
| 100~128k | 파일 통째 덤프 | — | 아래 3.1 참고 |

3.1 **128k의 현실성**: 32B·10인·128k는 b + 1.4×128×10 ≈ **1,870GB**가 필요해, 표의 어떤 장비로도 불가능합니다. 메모의 "비권장"이라는 결론은 맞고, 오히려 *"불가능"*에 가깝습니다. 또 Qwen 32B 계열의 기본 컨텍스트는 32k이고 그 이상은 YaRN 같은 확장에 의존하므로, 확장 품질 저하도 함께 고지해야 합니다.

3.2 **"32k 이상에서 Lost-in-the-middle 시작"** 은 정성적 주장입니다. 모델·태스크에 따라 다르고 이 계산기가 검증하는 값이 아니므로, 근거 문헌 없이 단정 표현은 피하는 것이 좋습니다. "에이전트가 보통 요약(Compaction)을 수행한다"는 설명은 제품마다 달라 일반화가 어렵습니다.

## 4. 가속기 스펙 검토

| 구성 | VRAM | 합산 대역폭(코드) | 검토 |
| :--- | :--- | :--- | :--- |
| H100 80GB ×1 | 80 | 3.35 TB/s | SXM 기준. PCIe H100은 약 2.0 TB/s |
| GB10(DGX Spark) | 128 | 273 GB/s | 통합 메모리라 OS 등과 공유, 전량 사용 불가. 대역폭이 병목이라는 서술은 정확 |
| A100 80GB ×2 | 160 | 4.08 TB/s | 2.04×2, 타당 |
| H100 80GB ×2 | 160 | 6.7 TB/s | 3.35×2, 타당 |
| H200 141GB ×2 | 282 | 9.6 TB/s | 4.8×2, 타당 |
| H100 80GB ×4 | 320 | 13.4 TB/s | 타당 |
| L40S 48GB (메모 버전) | 48 | 0.864 TB/s | PCIe·NVLink 없음, ×4 병렬 시 통신 병목 큼 |

- 멀티 GPU 대역폭을 **단순 합산**하는 것은 텐서 병렬(NVLink) 이상 조건입니다. NVLink 없는 PCIe 구성(L40S×4 등)에서는 과대평가됩니다.
- 메모의 "GB10은 3~4 tps": 1인·FP16 32B 이론 상한이 273/67 ≈ 4.1 tps이고, 현재 식은 1인 2.4 / 10인 1.8 tps를 냅니다. 메모의 수치는 **1인 이론 상한**에 가깝고, 10인 동시에서는 더 낮습니다.

## 5. 객관적 평가

### 잘 된 점
1. **구조가 설명 가능**: 고정비 + 선형 증가라는 단순 모델이라 비전문가에게 근거를 설명하기 쉽고, KV 수치가 모델 구조에서 실제로 유도됩니다(위 2장).
2. **두 가지 한계(용량·대역폭)를 분리**해서 보여주는 프레임이 의사결정에 유용합니다.
3. **비현실적 옵션(B200 등) 제거**, 장비 조합의 실제 구성 가능성을 고려한 점.
4. 입력이 3개뿐이라 팀 단위 1차 견적 도구로 적합합니다.

### 과대·과소평가 위험 (우선순위 순)
| # | 이슈 | 영향 | 방향 |
| :-- | :--- | :--- | :--- |
| 1 | **VRAM 100%를 사용 가능 용량으로 가정**. vLLM 기본 `gpu_memory_utilization`은 0.9 | 160GB·10인 한계 컨텍스트가 60k → **약 49k**, 320GB는 174k → 151k | 용량 과대평가 |
| 2 | **KV를 FP8로 가정**. 기본(auto/FP16) 설정이면 KV가 2배 | 동일 조건 최대 인원이 약 절반 | 용량 과대평가 |
| 3 | **tps 식이 N명 배치를 근사**: 실제 decode 한 스텝은 `가중치 + N×KV`를 읽음. 코드는 `가중치 + 1인 KV`에 임의 감쇠(2.5%/인) 적용 | 10인·32k에서 H100×2: 코드 45 tps vs 배치 모델 37 tps(약 20% 낙관) | 속도 과대평가 |
| 4 | **prefill(TTFT) 미반영**: 에이전트는 매 턴 컨텍스트를 재전송. 32B·32k prefill은 요청당 약 2 PFLOP | 10인이 동시에 요청하면 대기 시간 지배. Prefix Caching 효과도 모델 밖 | 체감 성능 과대평가 |
| 5 | **"동시 인원"이 전원 풀 컨텍스트를 점유한다고 가정**: 실제는 길이 분포·페이징으로 평균 점유가 작음 | 반대로 용량 과소평가 가능 | 보수적 |
| 6 | 멀티 GPU 통신 오버헤드, PCIe/NVLink 차이 미반영 | 4장 구성에서 tps 과대평가 | 속도 과대평가 |
| 7 | 단일 요청의 **버스트/큐잉**(동시 인원 vs 도착률) 미모델 | 피크 시 지연 과소평가 | 과대평가 |
| 8 | 모델 성능 서술("Sonnet급 코딩 에이전트 주력")은 계산 근거가 없는 마케팅성 문구 | 신뢰성 | — |

### 종합 판정
**1차 견적·보고용으로는 타당**하며 KV 산식과 가중치 값은 검증됩니다. 다만 용량 쪽은 1·2번 때문에 *현재 수치가 실제 vLLM 기본 설정보다 후하게* 나오고, 속도 쪽은 3·4·6번 때문에 낙관적입니다. 현재 값은 **"상한선(best case)"** 으로 표기하는 것이 정확하며, 구매·계약 근거로 쓰려면 실측 벤치마크와 안전 마진(권장: 용량 10~20%, 속도 20~30%)이 필요합니다.

## 6. 기능 검토 시 제안 (v2 업데이트 후보)
1. 사용 가능 메모리 비율(기본 0.9) 입력 추가, KV 정밀도(FP8/FP16) 토글
2. tps를 `BW_eff / (W + N·KV)` 식으로 교체, 멀티 GPU 효율 계수(NVLink/PCIe) 도입
3. 컨텍스트를 X축으로 한 그래프와 8종 장비(L40S 포함) 반영 — 메모 버전과 정합
4. prefill 시간(TTFT) 추정과 Prefix Cache 적중률 입력
5. 모델별 레이어·KV헤드 값을 데이터로 노출해 공식 투명성 확보
6. v1의 보정(Calibration)·Efficiency Factor를 v2로 이식 검토
7. "상한선 추정치" 문구와 안전 마진 표시

## 7. 한계
이 평가는 문서와 소스 정독, 공개 모델 구조 기반의 산술 검증이며 **실제 GPU 벤치마크는 수행하지 않았습니다.** 하드웨어 스펙(대역폭 등)은 공개 사양 기준의 기억에 의존하므로 반영 전 제조사 데이터시트로 재확인이 필요합니다.

## 8. 업데이트 반영 현황 (v2.1)

위 6장 후보 중 아래를 `index.html`에 반영했습니다. 반영 후 수치는 1~7장의 "현재 코드" 설명과 다릅니다(해당 장은 업데이트 전 기준의 평가 기록).

| 후보 | 반영 내용 |
| :--- | :--- |
| 1 사용 비율·KV 정밀도 | 고급 설정에 **사용 가능 VRAM 비율(기본 90%)**, **KV FP8/FP16 토글(기본 FP8)** 추가 |
| 2 tps 식·병렬 효율 | `tps = (BW × tpEff × MBU) / (가중치 + N × 1인 KV)`로 교체. 임의 감쇠 계수 제거 |
| 3 컨텍스트 축·8종 장비 | 그래프 X축 인원/컨텍스트 전환, 장비 9구성(L40S×1·×4, A100×4 추가), 한계선은 **사용 가능 용량** 기준 |
| 4 prefill/TTFT | `TTFT = 2 × 파라미터 × 미적중 토큰 / (TFLOPS × tpEff × 0.4)`, Prefix Cache 적중률 입력 추가 |
| 5 모델 구조 노출 | KV를 `2 × 레이어 × KV헤드 × head_dim × 바이트`로 코드에서 직접 계산 (상수 0.14 제거) |
| 6 보정 | MBU(대역폭 활용률) 슬라이더. v1의 `Efficiency Factor`에 대응 |
| 7 상한선 표기 | 하단에 상한선 추정치·안전 마진 안내 |

**가정치(출처 미확정, 실측으로 교정 필요)**: 멀티 GPU 병렬 효율 `tpEff`(NVLink 2장 0.9, 4장 0.8, PCIe L40S×4 0.6), prefill 활용률 0.4, GB10의 FP16 연산량 약 125 TFLOPS(공개 FP4 수치에서 환산한 근사), TTFT 허용 10초, 동시 활성 30~50%.

**남은 과제**: 요청 도착률·큐잉 모델, 평균 컨텍스트 분포(전원 풀 컨텍스트 가정 완화), 통합메모리 장비의 OS 점유 별도 모델, v1의 보정 데이터 입력/저장 기능.

## 9. 재검토 결과 (v2.2)

v2.1을 이론·단위·수식 관점에서 다시 검토하고, 브라우저 계산값을 독립 Python 재계산과 대조했습니다(9개 장비 × tps·TTFT·최대 인원, 소수 둘째 자리까지 일치).

| # | 발견 | 조치 |
| :-- | :--- | :--- |
| 1 | **단위 불일치**: 컨텍스트 `k`를 KV 계산에서는 1,000토큰, TTFT 계산에서는 1,024토큰으로 사용 (KV 약 2.4% 과소) | KV도 1,024토큰 기준으로 통일 (32B 32k: 4.19 → 4.29 GB/인) |
| 2 | **최대 인원이 메모리 기준만**: 표에서 "최대 16명"인데 속도 기준(28 tps)으로는 3명(A100×2)인 모순 표시 | 최대 인원 = min(메모리 기준, 속도 기준), 두 값을 함께 표기 |
| 3 | **prefill에 attention 항 누락**: 선형 항(2·P·n)만 사용 → 32k에서 약 30%, 128k에서 더 크게 과소 | `4·L·d·(n·T − n²/2)` 항 추가 (hidden size를 모델 데이터에 추가) |
| 4 | TTFT는 **단일 요청** 기준인데 표기가 없음 (N명이 동시에 도착하면 마지막 요청은 약 N배 대기) | 표 헤더에 "단일 요청 기준" 명시 |

**수정 후 기본값(32B FP16·10명·32k) 결과**: 필요 118GB, H100×2 추천(1인 34.5 tps, TTFT 4.0s, 메모리 기준 16명·속도 기준 15명 → **최대 15명**). A100×2는 21 tps로 속도 기준 3명, L40S×4는 12 tps로 0명.

**검증된 항목**: 모델 구조값(레이어·KV헤드·head_dim·hidden)과 가중치, 장비 대역폭·FP16 dense TFLOPS(GB10 제외), decode 식의 구조(가중치 1회 + N×KV 읽기).

**남은 한계(수정하지 않음)**: 병렬 효율·prefill 활용률·GB10 연산량은 가정치, 요청 도착률·큐잉 미모델, FP8 모델의 연산 이점 미반영(보수적), KV 읽기량을 전체 컨텍스트로 가정(상한), GB 단위는 십진/이진 혼용(약 5% 이내).

**판정**: 이론 구조와 계산은 정합하며, 위 4건을 수정한 뒤에는 "상한선 추정치"로서 1차 견적 용도에 적합합니다.
