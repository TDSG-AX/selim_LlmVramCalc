# v1 계산·이론 검수 결과

대상: `app.js`, `llm_performance_poc.py`, `concept_study_report.md`, `calibration_guide.md`, `index.html`. 코드는 수정하지 않았고 평가만 기록합니다. 수치는 공개 모델 구조(레이어·KV헤드·head_dim)로 산술 재계산한 값이며, 실제 GPU 벤치마크는 수행하지 않았습니다.

## 1. 계산 모델 요약
```
가중치      = P × bits/8
KV(1인)     = kvSafety × (P/8) × (seq/8192)         # GB, 파라미터 비례 휴리스틱
최대 인원   = floor((총VRAM − 가중치 − 예약 − 1.5) / KV(1인))
총 TPS      = (대역폭 × GPU수 / 가중치) × η           # η 기본 0.7
1인 TPS     = 총 TPS / 최대 인원
UM 장비     = η × 0.85, 예약 +1GB
```

## 2. 검증된 부분
- 가중치 계산(P × bits/8)과 "decode는 메모리 대역폭 바운드"라는 Roofline 설명은 타당합니다.
- GPU 사양(H100 3,352 / A100 2,039 / 1,555 / A6000 768 / 4090 1,008 / 3090 936 / MI300X 5,300 GB/s, M2 Ultra 800, GB10·ZGX 273, Z2 Mini 256)은 공개 사양과 대체로 일치합니다. M3 Max 400 GB/s는 128GB 구성(40코어 GPU) 기준입니다.
- PagedAttention 인용(기존 방식 메모리 60~80% 낭비 → vLLM 4% 이하)은 Kwon et al. (SOSP 2023)의 주장과 부합합니다.
- 보정 체계(η, 오버헤드, KV 안전계수)와 실측 보정 절차(`calibration_guide.md`)는 방법론으로서 합리적입니다.

## 5. 종합 평가
- **용량 계산**: 소형(8B급)에서는 근사치가 맞고 **모델이 커질수록 보수적(과소 인원)**. 구조 기반 KV로 교체하면 정확도가 크게 개선됩니다(v2 방식).
- **속도 계산**: **단일 스트림(batch=1) 이론치로만 타당**하며, 다중 사용자 1인 속도는 크게 과소 평가합니다. 즉 v1은 용량은 보수적, 속도는 비관적인 방향으로 틀립니다. 단, 멀티 GPU는 반대로 낙관적입니다.
- **문서**: 방법론과 보정 절차는 유용하지만, 4·5·6·8번 항목은 수정이 필요합니다.
- v1은 "보정 프레임워크가 있는 개념 검증용 계산기"로는 적합하나, 인원·속도 판단 근거로 단독 사용하기엔 위 1·2·3번 때문에 부적합합니다.

## 6. 개선 제안 (v1 유지 시)
1. KV를 `2×레이어×KV헤드×head_dim×KV바이트×토큰`으로 계산(모델 구조 입력 또는 프리셋 DB) — v2 `kvPer1k` 재사용
2. 1인 TPS를 `BW×η/(가중치+N×KV)`로 교체하고 tps 하한 판정을 상태 메시지에 반영
3. 멀티 GPU: 병렬 방식(TP/PP/DP) 선택과 효율 계수 도입, 문서 11장 수정
4. `|| default` 패턴을 `Number.isFinite` 검사로 교체
5. UM 장비는 사용 가능 비율(예약이 아닌 비율) 입력으로 모델링
6. 출처 없는 수치에는 근거를 달거나 "가정" 표기
